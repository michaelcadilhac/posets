Future reserve option, conceptual only (requested root question):
The additional assignments are consistent with reserve-before-insert: growth
can relocate the old array and then shift an interior suffix, where allocating
std::vector::insert could construct into final positions. Counters do not mark
individual growth sites, so this is source-supported, not a proven timing cause.
For safe_moves only, a no-victim insertion could reserve ranks first, allow the
vector insertion itself to allocate, and then insert the trivial int64 rank
without allocation. With all comparisons finished and rank capacity prepared,
allocation/length failure of the vector insert can leave logical contents
unchanged; noexcept V moves and nonallocating int64 insertion permit publication.
This is not achieved by simply deleting vector reserve in the current try:
mutated=true is set BEFORE vector_set.insert, so its bad_alloc would reach a
catch that clears both live arrays, violating the declared early-failure
guarantee. A future design must isolate the prepublication growth branch or
adjust its commit tracking, preserve cached-rank tie ordering/capacity-change
contract and the generic throwing-move staged fallback, and independently
exercise allocation/exception cases. Vector capacity growth is implementation
defined, so memory behavior also needs matched measurement. No code change or
measured benefit is asserted; consider only after the approved PMU evidence.
